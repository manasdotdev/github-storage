Let’s trace **one “place order” request** from the customer clicking a button to the order being saved.

## The pieces

- **Frontend:** runs in the customer’s browser. It can easily send ordinary HTTP requests using `fetch`.
- **Gateway/BFF:** a server-side HTTP endpoint designed for your frontend. It accepts HTTP/JSON and calls your backend over gRPC.
- **Order service:** your Go service. It receives the gRPC call, applies order rules, and stores the order.

```text
Browser                  Gateway/BFF                 Order service              Database
   │                           │                            │                        │
   │── HTTP + JSON ───────────>│                            │                        │
   │                           │── gRPC + Protobuf ────────>│                        │
   │                           │                            │── SQL query ──────────>│
   │                           │                            │<── saved order ────────│
   │                           │<── gRPC response ──────────│                        │
   │<── HTTP + JSON ───────────│                            │                        │
```

**HTTP/JSON** is the familiar web format: a URL, an HTTP method such as `POST`, and a JSON body. **gRPC** is a different way for backend services to communicate, using service methods and Protobuf messages. The gateway translates between them.

## The request, step by step

Suppose the customer clicks **Place order**. The frontend sends this HTTP request to your gateway:

```http
POST /api/orders
Content-Type: application/json

{
  "restaurantId": "r-123",
  "items": [
    {"menuItemId": "m-456", "quantity": 2}
  ]
}
```

The gateway receives it, checks things like whether the request is valid and who the customer is, then calls the order service’s gRPC method:

```text
CreateOrder(...)
```

The order service checks the business rules—for example, whether the items are available—and saves the order to the database. It sends a gRPC response back to the gateway. The gateway turns that into an HTTP response, perhaps:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"orderId": "o-789", "status": "PLACED"}
```

The frontend receives that response and can show “Order placed.”

## What does the gateway actually do?

At its core, it is a server with an HTTP route that calls a gRPC client. Conceptually:

```go
func createOrder(w http.ResponseWriter, r *http.Request) {
    // 1. Read JSON from the browser.
    // 2. Validate it and identify the customer.
    // 3. Call the order service using its gRPC client.
    // 4. Convert the result into JSON and send an HTTP response.
}
```

The gateway **does not need to contain the order’s business rules**. It translates requests and handles browser-facing concerns. The order service remains responsible for deciding whether an order can be placed.

## Where do Protobuf and gRPC fit?

You define the backend contract in a `.proto` file:

```proto
syntax = "proto3";

package orders.v1;

service Orders {
  rpc CreateOrder(CreateOrderRequest) returns (CreateOrderResponse);
}

message CreateOrderRequest {
  string restaurant_id = 1;
  repeated OrderItem items = 2;
}

message OrderItem {
  string menu_item_id = 1;
  int32 quantity = 2;
}

message CreateOrderResponse {
  string order_id = 1;
  string status = 2;
}
```

Code generation creates Go types and client/server interfaces from this file. The order service implements the server interface. The gateway uses the generated client to call it. This shared contract helps the two backend pieces agree on the shape of the request and response.

## Which gateway approach should you choose?

For your first version, I recommend a **small Go BFF**:

```text
frontend → HTTP routes in Go BFF → gRPC client → order service
```

It’s straightforward to follow and gives you flexibility to shape the API specifically for your frontend. For example, `/api/orders` can be a normal HTTP endpoint even though the BFF calls `CreateOrder` over gRPC behind the scenes.

**grpc-gateway** is another good option. It generates HTTP/JSON routes from your `.proto` definitions, so you write less translation code. It is useful when you want the HTTP API to closely follow your gRPC API. A BFF is more flexible when your frontend needs a different, user-focused API.

**gRPC-Web** is a way for a browser client to make gRPC-style calls, but it usually requires a compatible proxy and extra setup. You don’t need it to get started.

The key idea is: **the browser sends HTTP to a reachable web server; the gateway sends gRPC to the order service.** The gateway is the bridge.

The gateway reads the JSON, converts it into the generated Protobuf request, and calls the gRPC client:

```go

    Items: []*orderspb.OrderItem{
        {MenuItemId: "m-456", Quantity: 2},
    },
})
```

A simplified hand-written gateway might look like this:

```go
func createOrderHandler(client orderspb.OrdersClient) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        var body struct {
            RestaurantID string `json:"restaurantId"`
            Items        []struct {
                MenuItemID string `json:"menuItemId"`
                Quantity   int32  `json:"quantity"`
            } `json:"items"`
        }

        if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
            http.Error(w, "invalid JSON", http.StatusBadRequest)
            return
        }

        items := make([]*orderspb.OrderItem, 0, len(body.Items))
        for _, item := range body.Items {
            items = append(items, &orderspb.OrderItem{
                MenuItemId: item.MenuItemID,
                Quantity:   item.Quantity,
            })
        }

        // The gateway calls the order service over gRPC.
        result, err := client.CreateOrder(r.Context(), &orderspb.CreateOrderRequest{
            RestaurantId: body.RestaurantID,
            Items:        items,
        })
        if err != nil {
            http.Error(w, "could not create order", http.StatusInternalServerError)
            return
        }

        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(http.StatusCreated)
        _ = json.NewEncoder(w).Encode(map[string]string{
            "orderId": result.OrderId,
            "status":  result.Status,
        })
    }
}
```

This is illustrative; a production gateway also needs authentication, validation, sensible error-to-HTTP-status mapping, request limits, logging, and deadlines.

You’d register that handler on an HTTP server, for example:

```go
mux := http.NewServeMux()
mux.HandleFunc("POST /api/orders", createOrderHandler(ordersClient))

log.Fatal(http.ListenAndServe(":8080", mux))
```

The gateway needs a gRPC client connected to the order service. The order service runs its own gRPC server, perhaps on a separate internal port:

```text
Browser → gateway HTTP :8080 → order-service gRPC :9090
```

Only the gateway’s HTTP endpoint needs to be reachable by the browser. The gRPC port can stay inside your deployment network.

**Does this mean you’re “dealing with REST anyway”?** If you hand-write HTTP routes like `/api/orders`, you are creating an HTTP API, often designed in a REST-like style. But it’s not redundant: HTTP is the browser-facing interface, and gRPC is the service-to-service interface. You could instead generate the HTTP bridge from your `.proto` files with grpc-gateway, so you don’t hand-write the translation for every route. No—you don’t need that many RPCs. Several in your list are just different ways of asking for the same information, and some belong in other services or may not be needed at all.

For an order-service MVP, start with:

```proto
service Orders {
  rpc CreateOrder(CreateOrderRequest) returns (CreateOrderResponse);
  rpc GetOrder(GetOrderRequest) returns (GetOrderResponse);
  rpc ListOrders(ListOrdersRequest) returns (ListOrdersResponse);
  rpc CancelOrder(CancelOrderRequest) returns (CancelOrderResponse);
}
```

- **`CreateOrder`** — customer places an order.
- **`GetOrder`** — fetches one order, including its current status and details.
- **`ListOrders`** — lists the signed-in customer’s orders, usually with pagination.
- **`CancelOrder`** — cancels an order when its current state allows it.

A few important design points:

- Prefer **`CancelOrder` over `DeleteOrder`**. Real orders usually need to remain in the database for support, refunds, and audit history. Cancellation changes the order’s state; it doesn’t erase the record.
- You usually **don’t need `GetOrderStatus`** separately. Include the status in `GetOrder` and in each item returned by `ListOrders`.
- Don’t add a general **`UpdateOrder`** until you know what fields can be changed and under what rules. Changing an address, item, or quantity may have different restrictions depending on whether the restaurant has accepted the order.
- **Status changes** are usually explicit actions, not an unrestricted `UpdateOrderStatus`. For example, a restaurant might accept or reject an order, and a courier might mark it picked up or delivered. Add those operations when you build those workflows, and authorize them for the right role.
- History, summaries, metrics, and analytics can wait. Often the order response already provides the details needed for the main customer flow; reporting can be added later.

For example, `ListOrders` should support pagination rather than returning every order:

Think of `ListOrders` as asking the server:

## What pagination solves

Imagine a customer has 300 orders. Returning all of them at once is wasteful: it uses more database, server, and network resources, and makes the response slower. Instead, the server might return 20 at a time.

The first request could look like:

```text
page_size: 20
page_token: ""
```

An empty token means “start at the beginning.” The response might contain orders 1–20 and a token for the next page:

```text
orders: [order 1, order 2, ... order 20]
next_page_token: "opaque-token-A"
```

When the customer scrolls down and needs more, the frontend sends another request:

```text
page_size: 20
page_token: "opaque-token-A"
```

The server returns the next 20 orders and another token. When there are no more results, it returns an empty `next_page_token`.

The token is just a **continuation marker**: it tells the server where to continue. The client shouldn’t need to understand its contents; it should simply send it back.

## What `page_size` and `page_token` mean

```proto
message ListOrdersRequest {
  int32 page_size = 1;
  string page_token = 2;
}

message ListOrdersResponse {
  repeated Order orders = 1;
  string next_page_token = 2;
}
```

- `page_size`: the maximum number of orders the client wants. The server should enforce its own maximum—for example, if the client requests 10,000, the server might cap it at 100.
- `page_token`: where to continue from. It is empty for the first page.
- `orders`: the orders returned for this page.
- `next_page_token`: the token for the next page; empty when there are no more results.

You can picture it like reading a book: `page_size` is how many pages you want to read at once, and `page_token` is your bookmark.

## How does the server know whose orders to return?

The customer signs in. The frontend sends an authentication credential—commonly a session cookie or an access token—with its request. The server verifies it and learns the customer’s identity.

Then the request is conceptually:

> “List the next 20 orders belonging to the authenticated customer.”

Not:

> “List the next 20 orders belonging to customer ID `customer-123`, which the browser says it is.”

If the browser could choose the customer ID freely, someone might change it and try to view another person’s orders. The server should use the identity it verified from the authentication credential and check access on every request.

## Putting the ideas together

```text
1. Customer signs in.
2. Browser requests the first page of orders.
3. Server identifies the customer from the verified credential.
4. Server fetches up to 20 of that customer's orders.
5. Server returns those orders and a next-page token.
6. Browser sends that token when it needs the next page.
```

The pagination token controls **where to continue**; authentication determines **whose data may be returned**. They solve different problems.

One detail for a real implementation: return orders in a consistent order, usually newest first, and make the token opaque to the client. That helps avoid skipped or repeated results as the customer’s order list changes.

## 6. Enforce validation in the Go gRPC server

Adding rules to `.proto` files **does not automatically make grpc-go enforce them**. Add a Protovalidate interceptor when constructing the server. The Go runtime and gRPC middleware interceptor are separate Go dependencies. [6,7]

Then configure the server:

```go
package main

import (
	"log"

	"buf.build/go/protovalidate"
	protovalidateMiddleware "github.com/grpc-ecosystem/go-grpc-middleware/v2/interceptors/protovalidate"
	"google.golang.org/grpc"
)

func newGRPCServer() *grpc.Server {
	validator, err := protovalidate.New()
	if err != nil {
		log.Fatalf("create Protovalidate validator: %v", err)
	}

	return grpc.NewServer(
		grpc.ChainUnaryInterceptor(
			protovalidateMiddleware.UnaryServerInterceptor(validator),
		),
	)
}
```

A malformed RPC request is rejected before it reaches your handler, with a gRPC `InvalidArgument` error. If you add other interceptors—authentication, logging, tracing—chain them here too, and make sure your authorization checks still run for the relevant methods. [6]

For **this repository**, I’d use **one root `go.mod`**, and I’d keep that choice even as the app grows unless you have a concrete reason to version parts of the Go code independently.

The important distinction is:

> A Go module is a **Go dependency/versioning boundary**. It is not a deployment boundary.

You can still build and deploy `order-service` and `telemetry-service` as separate Docker images, with separate processes, scaling, configuration, and release workflows, while keeping them in one Go module. Separate deployment does **not** require separate `go.mod` files.

## Recommended structure

```text
grpc-dashdrop/
├── go.mod
├── go.sum
├── proto/
│   └── orders/v1/orders.proto
├── gen/
│   └── go/
│       └── orders/v1/
├── backend/
│   ├── order-service/
│   │   ├── cmd/server/main.go
│   │   └── internal/
│   └── telemetry-service/
│       ├── cmd/server/main.go
│       └── internal/
├── frontend/
├── deployments/
├── buf.yaml
├── buf.gen.yaml
└── Taskfile.yml
```

Remove the `go.mod` files inside the services, so the root module owns all Go code. Set the root module path to the import path you intend to use, for example:

```go
module github.com/YOUR_ORG/grpc-dashdrop

go 1.27
```

Then make the generated-code `go_package` match that module path:

```proto
option go_package =
    "github.com/YOUR_ORG/grpc-dashdrop/gen/go/orders/v1;ordersv1";
```

Both services can import the generated package directly. There’s no local `replace` directive or workspace setup to maintain. You can still build each service separately:

```bash
go build ./backend/order-service/cmd/server
go build ./backend/telemetry-service/cmd/server
```

And you can still deploy each as its own container. A single module doesn’t mean a single server or binary.

## When would separate modules be worth it?

Consider separate `go.mod` files if you reach a point where services genuinely need **independent Go dependency management or versioning**—for example, different teams own them, they release on separate schedules, or one service needs to consume a shared Go library as a versioned dependency.

That can be a good architecture, but it introduces real work: the generated API code must have a clear module and versioning strategy, local development needs coordination across modules, and CI must test each module correctly. Don’t create separate Go modules just because the code lives in separate service folders.

If you later do split them, make it a deliberate structure, such as:

```text
grpc-dashdrop/
├── api/                       # owns/version-controls generated API Go code
│   ├── go.mod
│   └── gen/go/orders/v1/
├── backend/
│   ├── order-service/
│   │   └── go.mod
│   └── telemetry-service/
│       └── go.mod
├── go.work                    # optional local multi-module development
└── ...
```

At that point, remove the root `go.mod`; don’t leave an unused root module alongside the service modules. The API module also needs its own compatibility and release policy, because services depend on its generated code.

**My recommendation:** use one root module now, keep the service folders and separate deployment artifacts, and split into Go modules only when independent Go dependency/version management becomes valuable. That gives you a scalable monorepo without taking on module-management complexity prematurely.
